How to run python code?

## 1. What is Python?

Python is a general-purpose programming language designed to be readable, expressive, and relatively easy to learn. It is widely used for data analysis, scientific computing, automation, web development, artificial intelligence, and many other applications. One of Python's strengths is its large ecosystem of reusable packages, which means that you can build on tools created by other developers rather than implementing everything yourself.

If you need to install Python on your own computer, follow the official Python installation and setup documentation:

[Official Python documentation and installation guide](https://docs.python.org/3/?utm_source=chatgpt.com)

For this course, use a recent **Python 3** release. After installation, you can check that Python is available from a terminal:

```bash
python --version
```

On some Linux and macOS systems, you may need to use:

```bash
python3 --version
```

If the command prints a Python 3 version number, Python is installed and available.

# 2. Google Colab and Jupyter Notebooks

For the first part of the course, **Google Colab is the recommended way to get started**. It allows you to run Python code in your web browser without having to install Python or most of the required packages locally.

A notebook consists of cells that can contain Python code, text, equations, visualisations, and other content. You can execute a code cell and immediately see its output.

Google Colab is based on the Jupyter notebook ecosystem and provides a convenient hosted Python environment.

## 2.1 Getting started with Google Colab

1. Open [Google Colab](https://colab.research.google.com/) in your browser.
2. Sign in with a Google account if required.
3. Create a new notebook.
4. Add a code cell.
5. Enter:

```python
print("Hello, Python!")
```

6. Run the cell using the play button next to it.

You can also install additional Python packages directly inside a Colab notebook using `pip`:

```python
!pip install pandas
```

The `!` tells the notebook to execute the command using the underlying system shell.

> **Important:** Colab provides a temporary computing environment. Packages and files installed during a session may not necessarily remain available when the runtime is restarted. For serious projects, keep your code and dependency information in a repository or project directory.

# 3. What is `pip`?

Python comes with a large **standard library**, but many useful tools are provided as separate packages. Examples include:

* `numpy` for numerical computing
* `pandas` for working with tabular data
* `matplotlib` for visualisation
* `scikit-learn` for machine learning
* `requests` for working with web services

`pip` is the standard Python tool for installing packages from the Python Package Index (PyPI) and other package sources.

For example:

```bash
python -m pip install numpy
```

or, on systems where Python is invoked as `python3`:

```bash
python3 -m pip install numpy
```

You can install several packages at once:

```bash
python -m pip install numpy pandas matplotlib
```

Using `python -m pip` is often preferable to simply typing `pip`, because it makes it explicit which Python installation is being used.

You can learn more about package installation in the official Python and pip documentation.

# 4. The `requirements.txt` file

Installing packages one at a time is convenient when experimenting, but it becomes problematic when you start sharing code.

Imagine that you write a project using:

```text
numpy
pandas
matplotlib
scikit-learn
```

A colleague downloads your project, but their computer does not have these packages installed. They need to know exactly what your project requires.

This is where **`requirements.txt`** becomes important.

A simple `requirements.txt` might look like this:

```text
numpy==2.3.2
pandas==2.3.1
matplotlib==3.10.5
scikit-learn==1.7.1
```

The file records the Python packages required by the project. In particular, specifying versions helps make the environment reproducible.

Another person can then create the environment and install everything with:

```bash
python -m pip install -r requirements.txt
```

### Why is this important?

Without a requirements file, you might say:

> "Install pandas and numpy."

But which versions?

A package can change over time. A newer version may introduce a new feature, remove an old feature, or behave differently from the version you originally used.

A requirements file therefore acts as a **recipe for recreating the software environment** used by your project.

This is vital for:

* sharing coursework with instructors and classmates;
* reproducing results;
* collaborating on projects;
* debugging problems;
* running code on another computer or server;
* deploying applications;
* preserving old projects.

A good rule is:

> **If a project depends on external Python packages, keep its dependencies documented in a requirements file.**

---

# 5. Virtual environments with `venv`

A second important concept is the **virtual environment**.

Suppose you have two Python projects:

* Project A requires version 1 of a package.
* Project B requires version 2 of the same package.

Installing both packages globally can create conflicts.

A virtual environment gives each project its own isolated collection of Python packages.

Python includes a built-in tool called `venv` for creating these environments.

## 5.1 Create a virtual environment

First, create a directory for your project:

```bash
mkdir my-python-project
cd my-python-project
```

Then create a virtual environment:

```bash
python -m venv .venv
```

The `.venv` directory contains the isolated environment.

## 5.2 Activate the environment

### macOS / Linux

```bash
source .venv/bin/activate
```

### Windows PowerShell

```powershell
.venv\Scripts\Activate.ps1
```

After activation, your terminal will usually show something like:

```text
(.venv)
```

This indicates that commands such as `python` and `pip` are now associated with the virtual environment.

## 5.3 Install packages

Once the environment is active:

```bash
python -m pip install numpy pandas matplotlib jupyterlab
```

You can then save the project's dependencies in `requirements.txt`.

For example:

```bash
python -m pip freeze > requirements.txt
```

Another computer can recreate the environment with:

```bash
python -m venv .venv
```

followed by activation and:

```bash
python -m pip install -r requirements.txt
```

This combination is a very useful basic reproducibility workflow:

```text
Project
├── .venv/
├── requirements.txt
├── notebooks/
└── scripts/
```

The `.venv` directory itself should generally **not** be committed to Git or uploaded with your project. It can be recreated from `requirements.txt`.

# 7. Run a Jupyter server yourself

An alternative to Colab is to run a Jupyter server on a local computer or on a cloud server.

This is useful when:

* you want more control over the Python environment;
* you have a powerful local machine;
* you need access to specialised hardware;
* you want to use a cloud virtual machine;
* you need notebooks to run for longer periods;
* you are working with datasets that are too large for a typical hosted environment.

## 7.1 Local Jupyter server

The basic process is:

1. Install Python.
2. Create a project directory.
3. Create a virtual environment.
4. Activate the virtual environment.
5. Install JupyterLab.
6. Install the packages required by your course or project.
7. Start the Jupyter server.

For example:

```bash
mkdir course-project
cd course-project

python -m venv .venv
```

Activate the environment and install Jupyter:

```bash
python -m pip install jupyterlab
```

Then start the server:

```bash
jupyter lab
```

The terminal will display a local URL, typically containing a security token. Open that URL in your browser.

---

# 8. Jupyter on a cloud server

A cloud server follows essentially the same basic pattern, but there is an important security difference: **the server is potentially accessible from the internet**.

A simplified workflow is:

1. Create a cloud virtual machine.
2. Connect to it using SSH.
3. Install Python.
4. Create a virtual environment.
5. Install JupyterLab and your project dependencies.
6. Start Jupyter.
7. Set up port access.
8. Access it securely from your own computer.

For example:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install jupyterlab
```

You should **not simply expose an unauthenticated Jupyter server directly to the public internet**.

For a basic setup, an SSH tunnel is often a safer approach. For example, if Jupyter is running on port `8888` on the remote server:

```bash
ssh -L 8888:localhost:8888 username@your-server
```

Then start Jupyter on the server:

```bash
jupyter lab --no-browser --port=8888
```

You can open the corresponding local address in your browser.

> **Security note:** Cloud-hosted Jupyter servers require additional security considerations, including authentication, firewall rules, HTTPS, user permissions, and keeping the operating system and software updated. Treat public-facing Jupyter servers as a system-administration task rather than simply another way to run a notebook.

# 10. Bonus: Running Jupyter with Docker

> **Advanced topic — not required for this stage of the course**
>
> Docker is powerful, but you do **not** need to learn Docker to complete the basic course exercises. Treat this section as an introduction to a technique you may encounter later in professional software development and research computing.

Docker allows you to package an application together with its software environment into a **container**. Instead of installing Python, Jupyter, and dozens of packages manually on every computer, you can describe the environment in configuration files and build a container containing everything you need.

This can make environments much easier to reproduce.

## 10.1 Why use Docker for Jupyter?

A Docker-based Jupyter environment can provide:

* a consistent Python version;
* a fixed collection of packages;
* an isolated environment;
* an easy way to recreate the environment;
* a convenient way to deploy Jupyter to a server;
* less dependency on the host computer's configuration.

The Jupyter project maintains **Jupyter Docker Stacks**, which provide ready-to-run Docker images containing Jupyter applications and related scientific computing tools.

[Jupyter Docker Stacks documentation and repository](https://github.com/jupyter/docker-stacks?utm_source=chatgpt.com)

## 10.2 The simplest approach

After installing Docker, you can use an existing Jupyter Docker image rather than building everything yourself.

For example:

```bash
docker run -p 8888:8888 \
    quay.io/jupyter/base-notebook:latest
```

The container starts a Jupyter server and maps its port `8888` to port `8888` on your computer.

The Jupyter Docker Stacks documentation provides more complete examples, including mounting a local directory into the container so that your notebooks remain available outside the container.

## 10.3 Building your own image

For a project that requires a specific environment, you can create a `Dockerfile`.

A simplified example is:

```dockerfile
FROM quay.io/jupyter/base-notebook:latest

COPY requirements.txt /tmp/requirements.txt

RUN pip install --no-cache-dir -r /tmp/requirements.txt
```

Your `requirements.txt` might contain:

```text
numpy==2.3.2
pandas==2.3.1
matplotlib==3.10.5
scikit-learn==1.7.1
```

You can then build the image:

```bash
docker build -t my-course-jupyter .
```

and run it:

```bash
docker run -p 8888:8888 my-course-jupyter
```

This illustrates an important idea: **`requirements.txt` and Docker complement each other**. The requirements file describes the Python packages, while the Dockerfile describes how the larger computing environment is constructed.

Docker's official Python guide also demonstrates installing dependencies from a `requirements.txt` file during image construction.

## 10.4 Why this is useful for reproducibility

Without containers, a project might depend on:

```text
Operating system
       ↓
Python version
       ↓
Virtual environment
       ↓
Python packages
       ↓
Jupyter
       ↓
Your code
```

Docker allows you to package a much larger portion of this stack into a reproducible container image.

This is particularly valuable for:

* research projects that need to be reproduced years later;
* teaching environments where every student should have the same setup;
* automated testing;
* cloud deployment;
* production systems;
* collaborative software projects.

However, Docker introduces additional concepts such as images, containers, volumes, networking, port mappings, security, and image management.

**For this course, you do not need Docker.** Start with Google Colab or a local Python + Jupyter + `venv` setup. Once those concepts are comfortable, Docker will be much easier to understand.

# Getting Started with Google Cloud Storage (GCS)

This guide explains how to access **Google Cloud Storage (GCS)**, create a new storage bucket, and upload data using the Google Cloud web console.

## 1. Accessing And Setting Up Google Cloud

1. Open the [Google Cloud Console](https://console.cloud.google.com/).
2. Sign in using your Google account.
3. Select the **Google Cloud project** you have been assigned.
4. At the top of the Google Cloud Console, open the project selector.
5. Select New Project if you need to create a project.
6. Enter a suitable project name.
7. Select the billing project/account.
8. Confirm that the correct project and billing information have been selected, then click Create.
9. In the navigation menu, select **Cloud Storage** → **Buckets**.

## 2. Create a New Bucket

A **bucket** is a container used to store files and data in Google Cloud.

1. On the **Cloud Storage → Buckets** page, click **Create**.
2. Enter a unique name for your bucket.

   * Bucket names must be globally unique.
   * Use a simple name such as `student-data-12345`.
   * Avoid spaces and special characters.
3. Choose the appropriate **location**. Use the location specified by your instructor if one has been provided.
4. For the remaining options, keep the default settings unless your instructor tells you otherwise.
5. Click **Create**.

Your new bucket should now appear in the list of buckets.

## 3. Upload Data to Your Bucket

1. Click the name of the bucket you just created.
2. Click **Upload files**.
3. Select the file or files you want to upload from your computer. [Sample Data](https://raw.githubusercontent.com/datasciencedojo/datasets/master/titanic.csv)
4. Wait for the upload to complete.
5. Your uploaded files will appear in the bucket.

You can also use **Upload folder** if you need to upload an entire folder of files.

## 4. Check Your Uploaded Data

After uploading:

1. Open your bucket.
2. Confirm that your file appears in the list.
3. Click the file name if you want to view its details.

## Important Notes

* **Do not upload sensitive or personal information** unless your instructor has explicitly asked you to do so.
* Keep your bucket and objects **private** unless you have been instructed to change their permissions.
* Make sure you are working in the **correct Google Cloud project**.
* Bucket names are globally unique, so you may need to add your student number or another unique identifier to the name.
* Delete test files and buckets when they are no longer required, if your course instructions allow it.

## Quick Summary

**Google Cloud Console → Select Project → Cloud Storage → Buckets → Create → Open Bucket → Upload files**

You have now created a GCS bucket and uploaded data to it using the Google Cloud web console.

Assess each criterion based on the quality and completeness of the team's description. Give **partial credit** when a criterion is addressed but lacks important detail.

## Peer-grading guidance

When assigning points, consider the following:

* **Full points:** The criterion is clearly addressed, sufficiently detailed, and appropriate for the project.
* **Partial points:** The criterion is addressed but is vague, incomplete, insufficiently justified, or missing important implementation details.
* **0 points:** The criterion is not addressed, or the proposed approach is fundamentally inappropriate.

### Important distinction

**Mentioning something is not the same as specifying it.**

For example:

* *Weak:* “We will store the data in the cloud.”
* *Stronger:* “Raw data will be stored in a GCS bucckets as JSON files. Processed feature tables will be stored as Parquet files. Each dataset release will have a version identifier and timestamp.”

Similarly:

* *Weak:* “We will split the data into training and testing data.”
* *Stronger:* “We will use a 70/15/15 train/dev/test split, stratified by the target class. The test set will be held out until final evaluation, and preprocessing parameters will be fitted using only the training data.”

### Overall peer-grading question

**Could another student, using this milestone description, understand how the project's data will be stored, accessed, transformed, split, and reproduced?**

If not, deduct points from the relevant criteria for missing specificity.

## 3. How to run the notebook

A notebook is made of **cells**. Text cells explain; code cells contain Python that you run.

| To do this | Do this |
|---|---|
| **Run one code cell** | Click the cell, then press the play button on its left, or press `Shift + Enter` (runs and moves on) or `Ctrl + Enter` (runs and stays). |
| **Run the cells above this one** | **Runtime > Run before**. Use this if you get an error saying something is "not defined". |
| **Edit a text cell** (written answers) | Double-click it, type, then press `Shift + Enter` to close it. |
| **Insert or delete a cell** | Hover between cells and click **+ Code**; to delete, use the bin icon at the top right of the cell. |
| **Undo** | `Ctrl + Z` (`Cmd + Z` on a Mac). |
| **Stop a cell that is running** | **Runtime > Interrupt execution**. |
| **Start again cleanly** | **Runtime > Restart session**, then run the Setup cells and the cells you need. |

The first time you run a cell, Colab connects to a computer in the cloud. This can take 10 to 20 seconds: wait for the cell to finish (the play button stops spinning).

> [!IMPORTANT]
> **Golden rule: run cells in order, from top to bottom.** Each cell uses results from the cells above it. If you skip one, later cells will say that something is "not defined".

## 5. What to do when something goes wrong

### Step 1: read the error from the bottom

Python errors are long, but the useful part is the **last line**. Read the last line first; it names the problem. Then look for the arrow (`---->`) that shows which line caused it.

```text
NameError                          Traceback (most recent call last)
/tmp/ipython-input-12.py in <cell line: 0>()
      3     "Survived is 0 or 1": ___,
----> 4     "Pclass is 1, 2 or 3": ___,
NameError: name '___' is not defined          <-- read this line first
```

| Error name | What it usually means |
|---|---|
| `NameError` | Python does not know that name. Either a blank (`___`) is still there, you misspelled a variable, or you did not run an earlier cell (use **Runtime > Run before**). |
| `KeyError` | A column name is misspelled. Names are case-sensitive: `"Pclass"` is not `"pclass"`. |
| `SyntaxError` | A typo in the code: a missing quote, bracket or comma. Look at the line with the arrow and the line just above it. |
| `TypeError` | The wrong kind of thing was used, for example a list where a number was expected, or a missing argument. |
| `ValueError` | The right kind of thing but a wrong value or shape, for example an array of the wrong length. |
| `AttributeError` | You used `.something` that does not exist for that object. Check the spelling: `.isna()`, `.mean()`, `.to_numpy()`. |

### Step 2: look up your problem

| What you see | Why it happens | What to do |
|---|---|---|
| `NameError: name '___' is not defined` | A blank is not filled in yet. | Replace `___` with your answer. This error is normal until you do. |
| `NameError: name 'df'` (or `'X_train'`, `'model'`, ...) `is not defined` | An earlier cell was not run, or the session restarted. | **Runtime > Run before** (on the cell with the error), then run it again. Cells with unfilled blanks above will show errors: fill them in. |
| `URLError`, `HTTPError`, or "Could not download" when loading the data | The network is blocking GitHub, or the internet dropped. | Upload `titanic.csv`: click the **folder icon** on the left, then the **upload icon**, and choose the file. Re-run the load cell (it falls back to `titanic.csv` automatically). |
| `CHECK AGAIN` | Your number is different from the expected one. | Re-read the blanks. Open the hint. Compare with the slide. Check quotes, brackets and the right data (`X_train`, not `X`). |
| Your number is slightly different from a neighbour's or the slide's | A different `random_state`, rounding, or a different split. | Use the exact values the task gives (for example `test_size=0.2`, `random_state=42`). The checks allow small rounding differences. |
| Red or pink text starting with `FutureWarning` or `UserWarning` | A warning, not an error. | Ignore it. The cell worked. |
| A cell has been running for a long time | Task 8 is the slowest. | Task 8 takes 5 to 15 seconds. If any cell runs for more than a minute, use **Runtime > Interrupt execution** and re-run it once. |
| The plot does not appear | The cell was interrupted, or has an error above the plot. | Run the cell again and read the last line of any error. |
| "Session crashed", "Runtime disconnected", or all your variables are gone | Colab disconnects after being idle, or memory ran out. | Click **Reconnect**. Then **Runtime > Restart session**, run the Setup cells, and use **Runtime > Run before** to get back to your task. |
| You deleted or broke a cell that was provided | Easy to do by accident. | Press `Ctrl + Z` straight away. Otherwise copy your blanks somewhere, re-open a fresh copy of the notebook and paste them back. |
| dtype shows `str` in one place and `object` in another | Different versions of pandas. | Ignore it. The two behave the same here. |
| A text cell shows symbols like `$$` or `\frac` | A formula that did not render. | Ignore it. It is only the formula. |
| You cannot sign in to Google | Some institutional accounts block Colab. | Use a personal Google account, or ask your lecturer for help. |

## 6. Quick tips for each task

| Task | Things that often trip people up |
|---|---|
| **1** | Use curly brackets `{ }` for the set of allowed values. Copy the pattern from slide 12 and only change the column and the values. |
| **2** | Use `.isna()` and then `.mean() * 100`, rounded to 1 decimal place. The two blanks in `assign()` are True/False columns (for Age and for Cabin). |
| **3** | The fence is Q3 + 1.5 x (Q3 - Q1): subtract the quartiles. For the share, divide by *all* first-class passengers (216), not by 891. |
| **4** | Use `dropna()` before sorting. The ranks start at 1, so the last ECDF value is exactly 1. |
| **5** | Cramér's V needs brackets: `np.sqrt(chi2 / (n * k))`. The method name goes in quotes: `method="wilson"`. |
| **6** | `"size"` and `"mean"` need quotes. The overall rate is total admitted divided by total applied, not the average of the department rates. |
| **7** | Give `train_test_split` the features `X` (not the whole `df`). Use the *training* numbers for the test rows. Use `np.nanmean` and `np.nanstd` with `axis=0`. |
| **8** | It takes 5 to 15 seconds. Run it once and wait. The checks only need the leaky score to be well above 0.5 and the pipeline score to be near 0.5. |
| **9** | Strategies and options need quotes: `"median"`, `"most_frequent"`, `"ignore"`. Fit on `X_train` and `y_train`; score on `X_test` and `y_test`. |
| **10** | Pass the whole `model` and the raw `X` and `y` to `cross_val_score`, not a transformed matrix. In your own finding row, include a number, an action and a limitation. |

### The two exercises

**Exercise 1: break it on purpose (Part 5).** The pipeline has rules about what a good row is. You write a small file containing one row that breaks each rule (a negative number of bikes, an empty station id, an unreadable time, a word instead of a number), one row that is odd but allowed (more bikes than the capacity), and one for an unknown station. **Before running anything you predict** the counters (`rows_read`, `good_rows`, `bad_rows`, `over_capacity`, `unknown_station`). Then you run it and compare. *The aim: understand the rules well enough to predict what happens.* Tip: the over-capacity row is *not* rejected, and `unknown_station` counts hourly **results**, not rows.

**Exercise 2: investigate the real results (Part 7).** In Part 6 a counter called `unknown_station` shows a large number. Using pandas on the pipeline's output you find **which stations** have no name, **when** they appear, and you write down why this might have happened and what you would ask the data owner. *The aim: see that a counter that fires on real data points to a real data problem.*

## 8. Frequently asked questions

**Do I need a Google Cloud account for this?** No. Colab needs only a normal Google account, and the notebook uses no Google Cloud project and no credits. The lab uses Google Cloud later.

**Do I hand anything in?** No. The checks and your written answers are for you.

**Do I need Google Colab?** No, but it is the easiest way and how the labs are done: see section 1a. You can also run the notebook on your own computer (section 4).

**Why Apache Beam for such a small job?** A million rows could also be handled with pandas alone, and for a job this size that would be simpler. Beam is used here because the same pipeline can run on a large cloud system (Google Cloud Dataflow) for much bigger data, which is what you will do in the lab. (The reconciliation in Part 6 actually uses pandas as the second method.)

**What if my numbers are slightly different from the notebook's?** For the sample data they must match exactly. For the real data, they may differ a little if the council has updated its files.

**Is the data free to use?** Yes, under the licence CC BY 4.0, with credit to Dublin City Council.
